# Operational Runbooks

These runbooks dictate standard operating procedures for resolving production incidents.

## 1. High CPU Usage / Application Unresponsive
**Symptoms:** P99 Latency spikes over 3s, HTTP 504 Gateway Timeouts, `HighResponseLatency` Prometheus alert fires.
**Action:**
1. Check Sentry for an influx of `Timeout` errors.
2. Check MongoDB Atlas for slow queries (un-indexed full collection scans).
3. If caused by a sudden traffic spike, dynamically scale the instances horizontally (e.g., `pm2 scale backend +2` or update Kubernetes HPA).
4. Restart the Node process if it appears deadlocked: `pm2 restart backend`.

## 2. Database Connectivity Loss
**Symptoms:** `Database not connected` in `/health/ready` probe, `BackendDown` alert, HTTP 503 errors.
**Action:**
1. Log into MongoDB Atlas Dashboard.
2. Check if the IP Access List (Whitelist) was accidentally modified.
3. Check the Network Peering / VPC settings if hosted in AWS.
4. Verify the `MONGO_URI` environment variable has not been changed.
5. The application will automatically attempt to reconnect via Mongoose; no application restart is strictly required, though it is recommended to flush the Agenda queue on reconnection.

## 3. Redis Eviction / Cache Failure
**Symptoms:** Redis connection errors in Pino logs, increased latency on read-heavy routes.
**Action:**
1. Verify Redis memory usage. If full, check if the eviction policy is correctly set to `allkeys-lru`.
2. Do **not** panic: The backend gracefully degrades to pulling data directly from MongoDB if Redis is unreachable.
3. Restart the Redis instance.
4. The backend will auto-reconnect and begin passively re-warming the cache as new requests arrive.

## 4. Deployment Rollback
**Symptoms:** A new deployment introduces breaking API changes or massive error rates (Sentry spikes).
**Action:**
1. In GitHub Actions, navigate to the previously successful `Release` workflow run.
2. Trigger a re-run of that exact job to deploy the previous Docker image / git commit.
3. Once the deployment succeeds, verify `/health` returns the rolled-back `appVersion`.
4. Run `npm run cache:flush` (or trigger the admin cache bust endpoint) to clear any cached data generated by the faulty version.
